# Stablecoin Whale Monitor v1 - architecture and operations

Version 1 was the original production MVP: two hand-configured Compute Engine
VMs running Node.js processes under systemd, with Nginx and a global external
Application Load Balancer serving the public application.

This document preserves the architecture, security model, operating procedure,
and main production incident from the `V1` [source snapshot](https://github.com/Josephdara/stablecoin-whale-monitor/tree/V1).
It is historical documentation. For the current system, return to the
[v3 README](../README.md) and [v3 deployment runbook](RUNBOOK.md).

## What v1 did

- Watched confirmed Ethereum mainnet blocks for large USDC and USDT `Transfer`
events.
- Stored each qualifying event as its own immutable JSON object.
- Kept the mutable checkpoint and token metadata in a separate state bucket.
- Served a read-only Express API from a web VM.
- Served a statically exported Next.js dashboard through Nginx.
- Used a private indexer VM with outbound access through Cloud NAT.
- Exposed only the global load balancer to normal web traffic.

Email alerting, Pub/Sub, containers, Cloud Run, GKE, Terraform, monitoring as
code, and Cloud Build pipelines were introduced in later versions.

## Architecture

```text
Ethereum mainnet JSON-RPC
          │
          ▼
Private Compute Engine VM: swm-indexer
  systemd: swm-indexer
          │
          ├── immutable event JSON ──▶ events bucket
          └── checkpoint/metadata ───▶ state bucket

Browser ── HTTPS ──▶ Global external Application Load Balancer
                         │ Certificate Manager + Cloud Armor + Cloud CDN
                         ▼
                 Public-subnet web VM
                   Nginx on port 80
                    ├── static Next.js export
                    └── /api/* ──▶ Express on 127.0.0.1:3001
                                          │
                                          ├── reads events bucket
                                          └── reads state bucket
```

The Google Cloud deployment used:

- a custom-mode VPC;
- a public web subnet;
- a private indexer subnet with Private Google Access;
- Cloud Router and Cloud NAT for indexer egress;
- one web VM and one private indexer VM;
- separate service accounts for the two workloads;
- separate event and application-state buckets;
- a global external Application Load Balancer;
- Certificate Manager-managed TLS;
- Cloud Armor Standard;
- Cloud CDN for static frontend assets;
- Nginx as the VM-local origin and reverse proxy; and
- systemd for process supervision.

The estate ran in Google Cloud's Toronto region, with the VMs in
`northamerica-northeast2-b`.

## Network and security model

The public internet did not connect directly to either Node.js process.

- DNS pointed to the global load-balancer address, not a VM address.
- TLS terminated at the load balancer.
- The web VM accepted HTTP only from Google's load-balancer and health-check
source ranges.
- Express listened on `127.0.0.1:3001`, behind Nginx.
- The indexer VM had no public inbound application path.
- Administrative SSH to the indexer passed through the web VM as a jump host.
- Application Default Credentials came from attached VM service accounts; no
service-account key file was installed.

The principal firewall rules were:


| Rule                           | Purpose                                                                   |
| ------------------------------ | ------------------------------------------------------------------------- |
| `swm-allow-lb-web`             | Permit Google Front End and health-check traffic to web VM TCP 80         |
| `swm-allow-admin-ssh`          | Permit administrator SSH to the web VM from one trusted public IPv4 `/32` |
| `swm-allow-web-to-indexer-ssh` | Permit the web VM to reach the private indexer over TCP 22                |


The indexer identity could create event objects and update application state.
The web/API identity could read both buckets but could not modify them.

## Data model and checkpoint safety

Version 1 wrote one deterministic object per transfer:

```text
events/ethereum/YYYY/MM/DD/<block>-<logIndex>-<txHash>.json
```

Cloud Storage was the canonical datastore rather than a SQL database. This kept
the initial system inexpensive and made events immutable, inspectable, and easy
to reconstruct into the API's in-memory index.

Checkpoint and token metadata were stored separately:

```text
ethereum/checkpoint.json
ethereum/token-metadata.json
```

The indexer advanced its checkpoint only after all qualifying events in the
range had been written or confirmed as already present. Event creation used a
generation precondition so a crash replay could treat an existing deterministic
object as success without permitting an accidental overwrite.

The confirmation buffer reduced short-chain-reorganization exposure. It did not
provide a finality guarantee, and v1 did not rewrite objects after a deep
reorganization.

## Processes and host layout

Application files were installed under:

```text
/opt/swm
```

Runtime configuration lived outside the checkout:

```text
/etc/swm/indexer.env
/etc/swm/api.env
```

The systemd units retained in `deploy/systemd` ran:

```text
swm-indexer.service
swm-api.service
```

Nginx used `deploy/nginx/swm.conf`. It served the static frontend and proxied
`/api` to the loopback API.

The services were enabled with:

```bash
sudo systemctl enable --now swm-indexer
sudo systemctl enable --now swm-api
sudo systemctl enable --now nginx
```

The service definitions applied host-level hardening including
`NoNewPrivileges=true`, `PrivateTmp=true`, `ProtectSystem=strict`,
`ProtectHome=true`, and restricted address families.

## Production configuration

Both processes used Cloud Storage:

```dotenv
STORAGE_BACKEND=gcs
GCS_EVENTS_BUCKET=<events-bucket>
GCS_STATE_BUCKET=<application-state-bucket>
```

The indexer used small logical and RPC ranges:

```dotenv
BLOCK_BATCH_SIZE=5
RPC_LOG_CHUNK_SIZE=5
POLL_INTERVAL_MS=15000
CONFIRMATION_BUFFER=6
```

The API bound only to loopback:

```dotenv
API_HOST=127.0.0.1
API_PORT=3001
API_REFRESH_MS=30000
API_MAX_PAGE_SIZE=50
```

The production frontend left `NEXT_PUBLIC_API_BASE_URL` empty so browser calls
used same-origin `/api/*` and Nginx performed the proxying.

## API in the v1 snapshot



### `GET /api/transfers`

Returned qualifying transfers in newest-first order. It supported `limit`,
`cursor`, `token`, `minimumAmount`, and address filtering.

### `GET /api/transfers/:txHash`

Returned every indexed qualifying transfer for a transaction.

### `GET /api/health`

Returned index and checkpoint health information.

### `GET /api/stats`

Returned daily aggregate statistics. The endpoint existed in the v1 backend
even after the frontend stopped displaying a statistics section.

The current API has evolved since this snapshot. Consult the v1 tag when
reproducing exact behavior.

```bash
sudo systemctl status swm-indexer swm-api nginx
sudo journalctl -u swm-indexer -n 100 --no-pager
sudo journalctl -u swm-api -n 100 --no-pager
```

Check the API directly on the web VM and through Nginx:

```bash
curl -fsS http://127.0.0.1:3001/api/health
curl -fsS http://127.0.0.1/api/health
```

## Production incident: API heap exhaustion

After the initial deployment, the frontend intermittently reported:

```text
Data could not be loaded.
Could not load transfer data (503)
```

The load balancer was healthy enough to route traffic, but the API process was
restarting. `journalctl` exposed V8 heap exhaustion:

```text
JavaScript heap out of memory
```

The refresh path repeatedly listed and downloaded every event object. As the
object count grew, overlapping refreshes increased memory consumption until the
Node.js process crashed.

The v1 fix:

- paginated the GCS listing;
- skipped object names already loaded;
- processed newly discovered objects incrementally;
- coalesced concurrent refresh requests; and
- replaced overlapping `setInterval` work with serialized `setTimeout`
scheduling.

This changed the steady-state operation from repeatedly rebuilding the entire
index to loading only newly created immutable events. The same object-count
pressure later motivated v2's NDJSON range-object format.

## Limitations that led to v2 and v3

- VM provisioning and application deployment were manual.
- Host patching, systemd, Nginx, firewall rules, and SSH access added operational
surface area.
- One-object-per-event storage amplified GCS listing and cold-start work.
- There was no event bus or email-alert consumer.
- There was no infrastructure state, reviewable Terraform plan, automated
monitoring configuration, or gated delivery pipeline.

Version 2 tested container portability and managed runtimes; see the
[v2 deployment playbook](PLAYBOOK.md). Version 3 made the managed design
reproducible and operationally controlled; see the [current README](../README.md)
and [deployment runbook](RUNBOOK.md).
